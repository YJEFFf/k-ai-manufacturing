## X-05 — Linux에서 한 명령 재현 실패: 확인

독립 Linux 실행에서 A/B 재적합 후 정상 예측의 `score`, `g_waveform` 요약이 현재 `verify._close` 기준을 통과하지 못했다. 정상 행 점수의 macOS 대비 최대 절대 차이는 A **0.000193925**, B **0.000228998**이다. 재적합한 저장 모델 4개의 SHA도 모두 달랐다. 반면 경보·알림·사건 등 정확 비교 열과 비유한 값 위치는 같았고, 정상 경보 행은 A 0·B 3, 이상 경보 행은 A 556·B 569로 유지됐다.

고정 macOS 모델을 재학습 없이 Linux에서 추론한 경우에는 B의 p값 3행도 최대 1/121만큼 달랐다. 이 경우에도 경보는 같았다. 따라서 단순히 JSON 저장 방식만의 차이로 축소할 수 없다.

독립 실험은 **주 결과 재현과 수치·파일 계약 재현을 분리**한다. 핵심 경보를 재현한다고 한 명령 실패가 사라지는 것은 아니며, 한 명령 실패가 곧 F1 오류라는 뜻도 아니다.

추가 원인들은 원 검수 로그와 코드로 확인했다.

- `press_guard/reproduce.py:45`~`:48`은 진단 기록을 만든 뒤 지도학습 표를 재생성한다. `analysis/press_evidence/build_diagnostics.py:1144`~`:1153`은 이 지도학습 표의 SHA를 기록한다. 새 표가 바이트 단위로 달라지면 앞선 기록이 낡는 순서다. Claude의 arm64·x86-64 로그에 해당 실패가 실제로 있다.

- `press_guard/test_time_order.py:132`~`:139`는 재적합 모델 4개의 바이트 SHA를 macOS 값으로 고정한다. 이번 Linux 재적합의 SHA 불일치로 해당 검사가 새 환경 재학습에 부적합함을 확인했다.

**정정할 주장:** 적대적 README 위쪽의 “원인은 … 5.0 Hz … 기저 퇴화”는 인과를 지나치게 확정한다. 이번 진단에서 5 Hz hat만 rank 2로 바꾸고 A/B를 재적합해도 정상 예측의 `score`·`g_waveform` 실패와 최대 차이가 그대로 남았다. 적대적 README 하단의 “원인 후보”가 더 적절하지만, 이것만 고치면 해당 실패가 해소된다는 가설은 이번 실험으로 지지되지 않았다.

**문서 범위:** `press_guard/README.md:205`의 다른 기기 부동소수 허용 설명에 실제 실패가 대응하므로 재현성 만점은 유지하기 어렵다. `README.md:24`의 Windows 표현은 이 검수에서도 Windows 실측이 없으므로 “지원 검증 완료”로 읽히지 않게 범위를 정해야 한다. Windows에서 실제 실패했다고 단정할 증거는 없다.

**Claude 수정 후 수락 조건:** 파일 변조를 검출하는 무결성 계약과 타 플랫폼의 의미적 동등성 계약을 구분하고, 경보·단계·사건·비유한 값 위치를 보존한 채 수치 안정성을 검증할 것. 실수 행 배치 변화도 잡아야 하므로 단순 허용오차 확대나 SHA 검사 삭제만으로 종결하지 말 것. 생성 의존 순서를 바로잡은 뒤 깨끗한 Linux x86-64 사본에서 README의 전체 명령을 끝까지 통과시킬 것. 지원한다고 명시할 다른 OS는 실제 실행 증거 또는 미검증 범위를 남길 것.

**수락 조건:** 이전 데이터 재전송과 수집 시계 오류를 구별할 수 있는 계약을 먼저 정할 것. 확인되지 않은 과거 행을 정상으로 간주하지 않으면서도 가용성 상실을 지속적으로 표시하고, 작업자 확인·재시작·복구 기준과 보류 시간 한계를 검증할 것. 단순히 큰 미래 시각을 무조건 버리는 규칙은 정상 장기 공백·시계 변경을 잘못 처리할 수 있으므로 별도 반례가 필요하다.

## C-04 — 재보정 검토 창의 필터 잔류: 현상 확인, 정책·시험 범위 한정

이상 600행을 5단위 감시창으로 나누고 첫 시각에 운전 변경 기록을 넣으면 첫 창은 “재보정 검토”가 된다. `--windows`의 함수는 첫 창 **150행을 남기고 450행을 제외**했다. “설비 점검 요청” 앞에 공백을 한 칸 넣으면 제외하지 않는 문자열 취약점도 확인됐다.

그러나 `monitor.py:163`~`:169`는 변경 기록 창을 이 필터의 대상에서 제외한다고 명시한다. `OPERATIONS.md:23`은 미확인 사건을 `--outcomes`로 빼고 `--windows`를 함께 쓰라고 적는다. `recalibrate.py:154`~`:158`도 두 필터를 순차 적용한다. **“변경 기록 하나만 넣으면 이상 자료로 재보정해 교체까지 통과한다”는 종단간 결함은 이번/원 검수 반례로 증명되지 않았다.** 입력은 별도 정상 CSV이고 이후 최소량·수락 검사가 남는다.

이는 알려진 변경과 고장이 동시 발생할 때 추가 확인이 없는 정책의 위험, 그리고 사람이 편집하는 CSV의 조치 문자열 처리 문제로 유지할 수 있다. “정책과 구현이 다르다” 또는 “아무 설명이 없다”는 지적은 아니다.

**수락 조건:** 변경 기록과 이상이 겹친 창, 옛/공백/미등록 조치 문구, `--outcomes` 유무를 포함해 자료 채택 정책을 명시하고 입력 검증할 것. 실제 재보정·수락·교체까지 실행해 오염 자료가 어디서 차단되는지 확인할 것.

## C-05 — 첫 경보의 운전 상태: 확인, 판정 시점 정정

A/B 각각 이상 **21/21 기록의 첫 경보가 `short`**라는 지적은 맞다. 이 상태는 경보를 막지 않는 사후 참고값이고 UI와 `OPERATIONS.md:29`가 판정 대기를 명시한다. `model.py:185`는 17번째 표본부터 상태를 내므로 표본 0을 기준으로 정확히 **1.6초 뒤**다. “1.7초 뒤”는 표본 수와 경과 시간을 섞은 근사다.

더구나 이상 **7/21 기록은 17행 미만**이어서 해당 기록 끝까지 상태가 나오지 않는다. “잠시 뒤 모두 갱신된다”로 설명해서는 안 된다. 판단표가 상태를 맨 먼저 요구하는 표현은 상태 미정일 때 근거·조치로 바로 진행하는 경로가 필요하다.

**수락 조건:** 첫 경보·짧은 기록의 “판정 대기”를 유효한 화면 상태로 취급하고, 상태가 나오기 전에도 경보 근거와 조치를 확인할 수 있음을 안내할 것. 상태를 내기 위해 경보를 늦추거나 미래 데이터를 사용해서는 안 된다.

## C-06 — 72.3·74.4·76.5%의 혼재: “낡은 값/반복 수 누락” 해석은 기각

`press_selection/README.md:110`~`:118`은 **별도 지속성 비용 실험**, **5회**, **seed 0~4**를 이미 명시한다. `:129`의 76.5%는 그 표의 원본 `fp_mitigation_injection_v2.csv`의 0.7653333333과 일치한다. 코드 `run.py:418`~`:422`와 결과의 `reps=5`도 같다. `README.md:139`는 E1과 다른 난수 실행이라고 설명한다.

반면 72.32%는 `fn_intensity_v2.csv`의 **50회**, seed 0~49 실험이다. 그 표 비고는 E1 74.4%가 다른 실행이라는 점까지 명시한다. 세 값은 같은 모델·같은 주입 강도의 서로 다른 몬테카를로 추정값이다. 4회차에서 모든 별도 실험을 50회로 통일해야 한다는 계약도 없다.

따라서 **“76.5%가 낡은 fn_intensity에서 잘못 남았다”, “반복 수를 적지 않았다”, “같은 실험의 값이 모순된다”는 근거는 없다.** 비교 문서마다 어떤 실험을 인용하는지 더 가까이 표시하는 편집 개선은 가능하지만, 수치를 억지로 맞추거나 기존 5회 실험을 오류로 분류해서는 안 된다.
