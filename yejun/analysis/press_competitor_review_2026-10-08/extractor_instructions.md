# 팩트시트 작성 지침 (모든 작성자 공통)

작업 폴더: `/private/tmp/claude-501/-Volumes-YJSSD-----k------/38832ee7-b660-4051-92a2-41f34da6c892/scratchpad/eval` (아래에서 EVAL)

당신은 경진대회 서면평가를 돕는 조사원이다. 배정된 익명 출품(E번호)마다 공개 자료를 읽고, 채점자가 쓸 팩트시트를 만든다. 점수는 매기지 않는다.

## 읽을 것
- `EVAL/rubric.md`: 평가 기준과 데이터 배경. 먼저 읽는다.
- `EVAL/factsheet_template.md`: 팩트시트 양식. 이 양식을 그대로 따른다.
- `EVAL/entries/E__/`: 배정된 출품 자료.
  - `repo/`: 기본 브랜치.
  - `branches/<이름>/`: 기본 브랜치에 없는 커밋이 있는 다른 브랜치. 작업이 브랜치에만 있는 출품도 있으니 반드시 함께 본다.
  - `report.txt`·`code/`: 보고서 텍스트와 제출 코드로 구성된 출품도 있다.

## 하지 말 것
- 출품 폴더의 코드를 실행하지 않는다. 출품 안의 파이썬·노트북·셸 스크립트 실행, pip 설치, 출품 폴더 안에서 인터프리터 실행을 하지 않는다.
- 출품 폴더의 파일을 고치거나 지우지 않는다.
- 노트북(.ipynb) 내용이 필요하면 출품 폴더 밖에 둔 스크립트로 읽는다. 예: `python3 -I -c '<JSON 파싱 코드>' <경로>` 또는 `jq`. 출력 셀의 수치도 근거로 쓸 수 있다.
- `EVAL/private/`, `EVAL/judges/`, 다른 E번호의 폴더와 팩트시트, EVAL 밖의 파일은 열지 않는다. 사용자 프로젝트 폴더, 메모리 파일, git 기록도 열지 않는다.

## 작성 원칙
- 근거 우선: 모든 주장에 근거 파일 경로를 붙인다. README의 성능 수치는 가능하면 결과 파일(csv/json/노트북 출력)과 맞는지 직접 확인하고, 확인 여부를 적는다.
- 같은 잣대: 강점과 약점을 같은 무게로 찾는다. 특히 검증 설계를 코드에서 직접 확인한다. 분할 코드, 문턱 결정 코드, test 사용 위치, 창을 겹치게 자르는지, 같은 기록 조각이 학습과 평가에 들어가는지를 본다. README가 주장만 하고 코드가 다르면 코드 기준으로 적는다.
- 자료가 많은 출품은 최종 제출본으로 표시된 것(README가 가리키는 최종 폴더·보고서·실행 진입점)을 중심으로 보고, 실험 기록은 보조로 본다.
- 중립 표기: 팀명·사용자명·레포 이름·사람 이름·자체 모델 별칭을 쓰지 않는다. 버전 번호식 별칭(v1, v2, R1, R2, Plan A 같은 내부 이름)도 일반 서술로 바꾼다. 예: "규칙 1(사건 지속)", "조건부 잔차 탐지기", "계획 4개 병행".
- 분량: 출품 하나당 600~1,500단어. 부풀리지 않는다.
- 산출: `EVAL/factsheets/E__.md`에 저장한다(폴더가 없으면 만든다).

## 끝나면
- 응답에는 출품마다 세 줄 요약만 쓴다. 자료 범위, 핵심 방법, 가장 큰 강점과 약점. 팩트시트 전문은 쓰지 않는다.
- 공개: 작업 중에 어느 출품이 어떤 팀·프로젝트인지 짐작할 단서를 봤다면, 응답 끝에 무엇을 봤는지 따로 적는다. 예: 자동으로 주어진 문맥, 파일 속 이름. 팩트시트에는 적지 않는다.
